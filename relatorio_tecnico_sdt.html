1. Introdução Teórica e Contextualização

A construção de um compilador é tradicionalmente dividida em duas grandes fases: a fase de Análise (Front-End) e a fase de Síntese (Back-End), intermediadas pela produção de uma Representação Intermediária (IR - Intermediate Representation).

Nas etapas pregressas do compilador didático MicroC, foram implementados o Analisador Léxico (conversão de caracteres em tokens), o Analisador Sintático (validação gramatical e estruturação na Árvore Sintática Abstrata - AST) e o Analisador Semântico (verificação de regras de tipo e tabela de símbolos em pilha de escopos). Uma vez validada a correção do programa-fonte na AST, surge a questão central da engenharia de software de compiladores: "Como transformar uma estrutura arbórea hierárquica em sequências lineares de instruções executáveis pelo computador?"

Distinção Formal: SDD vs. SDT
• Definição Dirigida por Sintaxe (SDD - Syntax-Directed Definition): É uma especificação formal puramente declarativa. Ela associa atributos (sintetizados ou herdados) às produções gramaticais e define equações matemáticas de avaliação sem prescrever explicitamente a ordem temporal de execução das ações.
• Tradução Dirigida por Sintaxe (SDT - Syntax-Directed Translation): É uma realização estritamente imperativa e procedimental. O SDT incorpora fragmentos de código (ações semânticas imperativas) diretamente aos percursos da árvore sintática. No MicroC, essas ações emitem código (emit()) de forma sequencial durante as visitas da AST.

A Analogia Pedagógica "Cardápio vs. Cozinha"

Para evitar o forte acoplamento entre a representação da linguagem e as rotinas de geração de código, o projeto adota rigorosamente a separação entre contrato e implementação:

  • O Cardápio (Contrato / Interface): Constituído pela interface ASTVisitor e pelas classes que definem a estrutura dos nós sintáticos (Nodes.java). O "cliente" apenas seleciona o que deseja visitar; a estrutura da árvore não sabe e não se importa com a forma como o código será gerado.
  • A Cozinha (Implementação das Ações Semânticas): Constituída pelas classes concretas de tradução (PostfixTranslator, TACTranslator, PrettyPrinter). Cada tradutor implementa sua própria "receita" de visita, gerenciando seus contadores, buffers de saída e estratégias de emissão.

Essa separação viabiliza o princípio didático de "Uma AST, Múltiplas Traduções": a mesma árvore permanece inalterada na memória enquanto três tradutores distintos geram saídas especializadas para pilhas (RPN), registradores (TAC) e formatação de texto (Pretty-Printer).

2. Arquitetura da Implementação

O compilador foi desenvolvido em Java 21, utilizando tipagem forte e desacoplamento via padrão de projeto Visitor. O percurso polimórfico é acionado pela invocação mútua entre o método accept(ASTVisitor visitor) dos nós da AST e os métodos visit(NodeType node) implementados pelos tradutores.

Variáveis de Estado do TACTranslator e o Canal Sintetizador lastPlace

A linearização de expressões aritméticas e estruturas de controle hierárquicas exige a gestão rigorosa de estados internos no gerador de código TAC:

  • tempCount: Contador numérico incremental responsável por nomear registradores temporários (ex.: t1, t2, ...).
  • labelCount: Contador numérico incremental responsável por emitir rótulos únicos de desvio de fluxo (ex.: L1, L2, ...).
  • instructions: Estrutura linear (lista encadeada) que armazena na ordem cronológica todas as instruções intermediárias emitidas.
  • actionLog: Vetor de log didático que registra cada decisão semântica tomada pelo compilador, facilitando inspeções e depurações.
  • loopStack: Pilha de contextos (Deque<LoopLabels>) para emissão precisa de saltos para break e continue em laços aninhados.
O Mecanismo de lastPlace como Canal de Comunicação
Como os métodos do padrão Visitor na interface ASTVisitor retornam void para preservar a genericidade do percurso, faz-se necessária uma forma de transferir o resultado de uma subexpressão filha para o nó pai que a engloba. No TACTranslator, isso é solucionado pela variável sintetizadora lastPlace.
Quando um nó filho (como NumberNode, IdentifierNode ou uma operação BinOpNode) termina seu processamento, ele grava em lastPlace o nome do registrador ou constante onde seu valor está alocado. O nó pai imediatamente consome esse valor como operando da sua própria instrução. 
// Exemplo didático do funcionamento de lastPlace em BinOpNode:
node.left.accept(this);
String left = lastPlace;      // Pai captura o operando esquerdo

node.right.accept(this);
String right = lastPlace;     // Pai captura o operando direito

String temp = newTemp();      // Aloca registrador para o resultado
emit(temp + " = " + left + " " + node.op + " " + right);
lastPlace = temp;             // Comunica para o nível superior que o valor agora está em 'temp'

3. Os Três Tradutores Obrigatórios

3.1 Tradutor 1: PostfixTranslator (Notação Polonesa Reversa / RPN)

O PostfixTranslator percorre as subárvores de expressões aplicando um caminhamento estritamente pós-ordem. O princípio fundamental da RPN consiste em visitar primeiro todos os operandos (da esquerda e da direita) e apenas depois disparar a ação semântica emit() para o operador. A notação pós-fixa dispensa qualquer uso de parênteses, sendo a representação ideal para máquinas virtuais baseadas em pilha (como a JVM e EVM).

  • Expressão de Entrada: 3 + 4 * 5
  • Fluxo Emitido: 3 4 5 * + (comprova visualmente que o produto 4 * 5 precede a soma com 3).

3.2 Tradutor 2: TACTranslator (Código de Três Endereços - TAC / IR)

O TACTranslator converte a árvore em instruções lineares onde cada comando possui no máximo um operador e no máximo três endereços (formato destino = op1 operador op2). Para o controle de fluxo, o tradutor realiza a decomposição linear das estruturas hierárquicas através de saltos condicionais (ifFalse) e incondicionais (goto):

  • Linearização de IfNode: Avalia a expressão de condição $\rightarrow$ emite ifFalse cond goto L_else $\rightarrow$ visita corpo then $\rightarrow$ emite goto L_end $\rightarrow$ rotula L_else: $\rightarrow$ visita corpo else $\rightarrow$ rotula L_end:.
  • Linearização de WhileNode: Rotula L_start: $\rightarrow$ avalia a condição do laço $\rightarrow$ emite ifFalse cond goto L_end $\rightarrow$ visita corpo do laço $\rightarrow$ emite goto L_start $\rightarrow$ rotula L_end:.

3.3 Tradutor 3: PrettyPrinter (Reimpressor Canônico e Linter)

Demonstrando a aplicação do SDT em ferramentas de engenharia de software (como Prettier e Clang-Format), o PrettyPrinter reconstrói o código-fonte em linguagem MicroC perfeitamente padronizado:

  • Utiliza a variável interna indentLevel para garantir tabulação consistente de 4 espaços por nível de aninhamento de blocos { }.
  • Insere parênteses canônicos em todas as expressões binárias para explicitar visualmente a árvore resolvida pelo analisador sintático (ex.: int x = (2 + (3 * 4));).

4. Detalhamento das Três Melhorias Avançadas Implementadas

4.1 Melhoria 1: Dobra de Constantes em Tempo de SDT (Constant Folding)

A técnica de Constant Folding (dobramento de constantes) avalia operações aritméticas e relacionais cujos operandos são conhecidos em tempo de compilação. Em vez de delegar operações redundantes ao processador em tempo de execução, o compilador calcula o resultado no momento do percurso sintático e injeta o literal numérico diretamente em lastPlace, sem emitir instruções e sem alocar variáveis temporárias.

Integração com a Tabela de Símbolos:

  • Symbol.java: Campo Category.CONSTANT, atributo constantValue e método verificador isConstant().
  • SymbolTable.java: Métodos de consulta e propagação isConstant(name) e getConstantValue(name).
  • TACTranslator.java: Métodos auxiliares resolveConstant(node, place) e computeConstant(op, left, right), com tratamento seguro para prevenir divisões por zero em tempo de compilação.

4.2 Melhoria 2: Reuso Inteligente de Variáveis Temporárias (TempPool)

Em implementações ingênuas, o compilador aloca novas variáveis temporárias sequenciais de forma ilimitada (t1, t2, ..., t50). Em hardware real, a quantidade de registradores é fisicamente finita. A classe TempPool implementa a análise de ciclo de vida (Liveness Analysis): assim que um nó pai consome o valor de suas variáveis temporárias filhas, essas temporárias são consideradas "mortas" e são devolvidas ao pool via releaseTemp().

Estrutura de Dados do Pool:

  • freeTemps: Fila de prioridade (PriorityQueue<Integer>) que garante a reutilização prioritária do registrador de menor índice disponível.
  • activeTemps: Conjunto ordenado (TreeSet<Integer>) que mantém as temporárias em uso concorrente na árvore de avaliação.

4.3 Melhoria 5: Comandos de Salto break e continue com Pilha de Laços (loopStack)

O suporte robusto aos comandos break e continue em linguagens de programação exige controle de contexto quando existem laços aninhados. No TACTranslator, essa funcionalidade é gerida por uma pilha de contextos do tipo Deque<LoopLabels> loopStack: 

public static class LoopLabels {
    public final String start;
    public final String end;
    public LoopLabels(String start, String end) {
        this.start = start;
        this.end = end;
    }
}

// No percurso de WhileNode:
loopStack.push(new LoopLabels(lStart, lEnd));
try {
    node.body.accept(this);
} finally {
    loopStack.pop();
}

// Ação semântica de break:
emit("goto " + loopStack.peek().end, "Break: desvio para fim do laço");

// Ação semântica de continue:
emit("goto " + loopStack.peek().start, "Continue: desvio para início do laço");

Validação Semântica Integrada: Caso o comando break ou continue seja utilizado fora de um laço de repetição (como no escopo global ou dentro de um bloco if/else sem laço envolvente), o SemanticAnalyzer acusa formalmente as regras de erro R8-BreakForaDeLaco ou R9-ContinueForaDeLaco, e o TACTranslator impede a emissão de código inconsistente.

6. Conclusões

A implementação do módulo de Tradução Dirigida por Sintaxe e das otimizações no compilador MicroC demonstrou de maneira prática a relevância de uma representação intermediária independente da máquina.

Ao adotar a filosofia de "Uma AST, Múltiplas Traduções", comprovou-se que o uso do padrão Visitor confere extrema modularidade ao sistema, permitindo que a mesma representação arbórea alimente saídas para máquinas de pilha (RPN), formatadores canônicos (Pretty-Printer) e geradores industriais de código linear (TAC). A implementação completa das três melhorias avançadas (Constant Folding, TempPool e loopStack) aliada a uma suíte de 53 verificações automatizadas consolida com pleno rigor técnico a fase de síntese e deixa o compilador preparado para as etapas subsequentes de geração de código para arquitetura-alvo (Back-End).
